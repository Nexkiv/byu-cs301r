* What is a large language model? How do they work?
	* A large language model (LLM) is a AI tool that uses tokens, or word parts, to form sentences. It accomplishes this by parsing user input into tokens then using a process of next token selection is forms a response. LLMs use both user input and previously generted tokens to generate new tokens. In addition to token pereditiction, LLMs can be trained on a contrained data set and output scope to refine possible outputs to be in line with the developer's constraints.
* What are a few tradeoffs of using LLMs with more or fewer parameters?
	* LLM's parameters effect the model's ability to reason and to generate applicable results. It should be noted though that the number of prameters is not the only trait that effects its accuracy. A model that is trained on a larger dataset is more effective than one which is trained on a smaller dataset even when the former has fewer parameters. More parameters also corilate to increased energy costs, so there is a diminishing return to the number of paramters. 
* What is a prompt?
	* A prompt for an LLM is a block of text or other input that is parsed by an LLM and then used to generate a response. The prompt establishes the role and goal of the LLM for the conversation. It also contains the user provided instructions for how to accomplish the specific request. It also establishes the context of the query to provide requisite information. The prompt then consists of the input or the specific data to be processed. Finally a prompt describes the prefered output format. A prompt does not have to contain all of these things, most times the goal and data are all that are used; however, LLMs are shown to be more effective when all of these elemts are included. 
* What is a token?
	* A token is the smallest atomic element of what an LLM performs actions on. They usually consist of about 3 to 4 characters and make up word parts or small words. The number of tokens is used to describe a context window that an LLM is cabable of pulling from. 

### Section 1b: Prompt Engineering

* Describe "zero-shot", "few-shot"
	* Zero-shot and few-shot are concepts in the subdomain of prompt engineering that refer to the number of examples given with the task description. Zero-shot is when the task given to the model does not contain any examples. This kind of prompt or task then relies entirely on the pre-training of the model. Zero-shot is most effective when handling simple or general tasks that are well-prepresented in the model's training data. Zero-shot, though, is much more limited when tackling a novel problem and in that case leads to unpredictable or incomplete performance by the model on the task. Few-shot is a different paradigm that involves including a few input/output examples along with the task. This allows for the model to be guided towards a desired format or behavior. This makes few-shot more effective at handling domain-specific and complex tasks.

This would most likely have the desired results because Claude was trained on programming examples and both python and the recursion/iteration tasks are common tasks. The zero-shot approach may struggle in the case where the function is complex or have an uncommon pattern. An example of when I might use a few-shot approach would be in asking Gemini to summarize an article into a specific format to be put into a database. I would provide the headers and sample length of each section. Because Gemini is trained on a large amount of internet text, it has a strong language comprehension and summarization ability. By providing sample input and output requirements/formating I am guiding the model to accomplish the summarization task in a specific way. The few-shot approach also has the trade-off of requireing more tokens and the examples have to be carefully chosen to make the llm reflect the desired response.
* What is "structured output"? What are the advantages of structured output?
	* Structured output is an API-level feature that is defined by the user. The user provides a schema that the model's output is guarenteed to conform to. This consistency is what makes the use of structured output effective. One common use of structured output is to force the model's output to conform to a specific JSON format. This limitation makes it so the response from the model can then be passed as input to other functions or displayed to the user. By having the model organize the data itself it saves the user the translation step of matching a blob of text to a specific format themselves. Other advantages include predictablity, easier validation, reduced hallucinated fields, and seamless downstream integration. Structured output can be used with other formats like XML, Markdown, or even custom schema.

These hallucinations can range from incorrectly performing math to expressing confidence in an incorrect answer. Hallucinations occur when the model does not have enough context, either from the prompt or the training set, to successfully complete the task of the prompt. These come from biases or gaps in the training data, ambiguous or under-contrained prompts, or just the probabolistic nature of token prediction. When brought into the field of agent engineering, these hallucinations can lead to incorrect tool calls or the wrong decisions about how to interface with other processes. Hallucinations can occur on any level for example: the prompt-level, the memory-level, the tool-level, or the reasoning-level.

### Section 1d: Jailbreaking

* What is context drift?
	* Context drift is the gradual degration or distortion of a conversational state brought upon by the limited storage of context or ambiguous user language. This is caused by the technical limitation of the models to only be able to use a finite amount of memory to keep track of context for any given circumstance. Context drift is something that will occur becuase it is a passive emergent behavior; however, it can also be exploited to lead to harmful effects. This is especially important in the process of jailbreaking where an individual is able to manouver an agent into taking an action that it has been set to not allow by influencing the agents perspective of the situation and its rules. Context drift is not the same thing as hallucination. Where halucination is fabricating false information, context drift is forgetting or ignoring established information within the current conversation. In an agentic circumstance, context drift can result in agents taking actions that deviate from an original goal or cause them to re-plan unessisarily. 
* Define jail-breaking. Provide a few examples of jail-breaking techniques.

This was circumvented by teenagers who found that by using inapropriate terms and induendos not on the list they could get the chatbot to act is inapropriate and in a few cases harmful ways. Another way to jail-break a model is to take advantage of contexct drift and get the model to care less and less about its inital instructions until it ignores them and listens to the attackers requests. Another form of jailbreaking involves seeding responses. When the attacker has access to the chat history and can modify it, they can make the model act as if it had said something in the past changing its current behavior based on incorrectly seeded past behavior. Some other jail-breaking tecniques involve role-play exploits and hypothetical framings of situations.

### Section 1e: Reasoning

* What is chain-of-thought prompting? Why is becoming less useful as models evolve?
	* Chain-of-thought prompting is the process by which a user would make a request to a model and ask it to explain each of its logical steps before presenting an answer this can be done explicitly, by asking for each step, or implicitly, by asking the model to think step-by-step. This process significantly improves performance on math and logic problems which a llm would normally struggle with. During a prompt engineering internship I had, one method we found for summarizing long documents into a single, short sentence was to have the model first rewrite the prompt then rewrite the bulk of the paper and finally it would provide the sentence. This process was the most effective because it doubled the context relating to the specific task. This reason chain-of-thought prompting has become less useful is with the emergence of reasoning models, the agents have become more effective at walking through the logic now as reasoning and it also decreases the amount of tokens used in a chat especially because reasoning tokens are seperate so the final response is consice and can benefit from structured reasoning. Technically, chain-of-thought prompting still has it uses with non-reasoning models and for transparency or debugging purposes.
* When designing an agent, when should you not rely on LLM reasoning? Give one example.
	* Reasoning allows for a model to be more effective at solving problems by relying on its patterns establish during training. One case where this would not be helpful would be the case of specific arithmetic or symbolic computation. In these cases the reasoning of an LLM is not suited for performing this task and it is better to be offloaded onto a tool call or something similar instead. This is because LLMs work through token prediction which involves taking advantage of the natural flow of language. Mathematics is rule-based and deterministic while language is more probabolistic. There isn't really a close enough when adding two numbers because there is only one answer. The problem comes when trying to do a specific mathematical example like totaling up the prices of items in a user's digital cart. Other times when reasoning would be unhelpful would be in real-time data lookups or deterministic business logic.

### Section 2a: RAG

* What is an embedding?
	* Embeddings are a numerical vector representation of data. This mapping of data makes it so elements that are semantically similar are positioned close together. The inverse is also true, where concepts that are not similar like a mathematical equasion and a noun are not close to each other in a vector space. This makes it so there is a direct relationship between meaning and location. Anything that can be expressed as data (images, text, audio, user behavior, etc.) can be expressed as an embedding. Embeddings are created by embedding models that are seperate from LLMs. These embeddings are useful because they allow LLMs to 'understand' relationships between concepts. Not in the cognitive way that we relate objects but instead as the proximity of the embedded vectors. These embeddings are commonly then stored in a vector database that can be used in RAG systems that allow for quick and effective search of relevant terms.
* When embedding text, why does chunk size matter?
	* Chunk size is significant in the embedding of text because of the mapping mentioned above that is done by embedding models. If the chunk size was a whole book all that would be embeded was the feel, tone, or themes of the book. If the chunk size was a chapter then the major plot points, significant characters, or locations would most likely get embedded. If the chunk size was paragraphs the specific information, dialogue, or sentence flow would most likely get encoded. If the chunk size is about a sentence then not a lot of story information would get encoded and it would mostly focus on phrasing or word choice. If the chunk size is word based then very little story information would get encoded and the database would fall back on standard encodings where words like man and king are related, and the main character's name might get connected with King if he is a king but it wouldn't be clear by looking at the embeddings what he did or accomplished. Chunking does alleviate some of these challenges by allowing for chunk overlap so context can be carried through by allowing for chunks to overlap as in the chapter or sentence example. Chunk size also is important in retreival where for the above examples the chunk size will affect what the user is able to search from among the embedded vectors. This makes it so the developer choosing the chunk size is making a descision between precise retreival of facts vs broader context to answer a question. It should be noted that there is a technical chunk size maximum so too large of chunks actually end up getting truncated instead of diluted.

### Section 2b: RAG Solutions

* What are some benefits of using RAG instead of just relying on an LLM’s internal knowledge?
	* A RAG system offers some key benefits that a default LLM couldn't do. For example, a RAG system is capable of pulling information from a direct source. This makes it so when an answer doesn't exist in the sources the model will state ignorance rather than hallucinating. This is because a RAG system makes the LLM ground its responses on retrieved text rather than on pattern matching. Also a RAG system can be built using a specific manual of style or novel data set that can then be retrieved. In both of those situations are ones where you would want the provided data to supersede the default training data. Another benefit of RAG systems is their ability to be up-to-date. LLMs by design are only as up to date as their training set is, but by building on a RAG system it makes it possible to access relevant recent information. RAG models are also capable of citing their sources making it possible for RAG to provide legal or medical information and then point to the source of where that information came from. RAG models are also effective at being transferable between domains. For a RAG system to be transferred all that needs to change is the knowledge base which saves on the expensive training costs. Because of their focused functionality RAG models also are less resourse intensive because the system will only pull from relevant sources. 
* Describe how the retriever and generator in a traditional RAG system works.
	* A traditional RAG system consists of three steps. First is the building of the RAG system. This is done by encoding the information that the RAG system will pull from. The encoding is done using embedding systems that are distinct from generative LLMs. Those encodings are then indexed in the vector database for quick retreival. The next step is done during generation time. When a RAG system is being used the user's prompt is first compared with the RAG system's vector database to retrieve relevant information. This is done by embeding the query itself as a vector and then performing a vector similarity search to find the closest matches. Those relevant chunks of encoded files are then passed to the LLM system which then generates a response using the provided files as context. This is done in a way that synthesizes the retrieved chunks with the original query into a coherent and grounded response. The context that was retrieved from the vector database is used as constraints and information instead of just being appended to the previous context.
* What is the role of a vector database in RAG?
	* A vector database is the place where stored embeddings of chunks are stored. These chunks are then used for lookups duing the retrieval step of a RAG system. The retrival is done using a vector similarity search which vector databases are engineered to be efficient at. Vector databases are constructed using embedding functions that process several chunks of data and then store them in this easy look-up storage. The databases also index the vectors to make similarity earches fast at scale usually using something like the Hierarchical Navigable Small World approach. In adsition to the indexing and the storage of the vecotors themselves the database also keepos track of metadata like page numbers so when a page is retreived its adjascent pages can also be retrieved. Vector databases, because of the nature of embeddings, are capible of semantic search instead of just keyword search. This means that if someone is making a query using the terms "war" and "boats" they will probobly get results about battleships even if the terms "war" and "boat" didn't appear in that specific chunk. This makes vector databases more effective than relational database for information searching because relational databases are limited to exact match or keyword searches.

### Section 2d: Tool Calling

* How does tool calling work with agents?
	* Tool calling is accomplished by giving agents access to specific tools to complement their semantic systems. More specifically, when a user makes a call to an agentic model, they can provide the model with a list of tools and how those tools are intended to be used. The agent then operates in a loop, the agent then will start to formulate a response and when it gets to the point that it wants to access something that a tool would help it understand, it makes a tool call. To make that call, it outputs a structured response containing the tool's name and the parameters to pass to it. The system in charge of handling the tool calls, usually called an orchestrator, then takes those inputs and runs the tool and then passes the output back to the model as context. This loop continues until the model generates a final text-only response. Some common tools are calculators, web searches, APIs, database-queries, and any other time when a deterministic or up-to-date response is more valuable than a semantic response.
* In what kinds of situations should tool calling be used?
	* In a general sense, tool calling is best used when it is providing the model with deterministic or up-to-date information that is more valuable than what the agent would generate as a semantic response on its own. As a specific example, when making a tool that calculates the road conditions at DisneyLand it would be helpful to have a tool call to get access to the local weather and another tool call to get access to the current traffic situation. Both things are time dependent and the model would not be able to generate an accurate response without that information. Another situation when tool calling would be appropriate would been when attempting to summarize information in a data-sheet. Using tool calls the model would be able to calculate the mean and median of data markers using mathematics. The model also would be able to make structed tool calls like assembling a SQL query based on a users request for information on a specific topic. In addition to the information retrieval ability of tool calls, they also can be used for taking action for example turning down lighting in a room and turning on relaxing music if a user makes a request to make a room's atmosphere more calm to a model that has access to those tools. Finally, tool calls also allow for the use of authenticated services like APIs so a model can gain access to information that is private and did not have the ability to be trained on.

### Section 2e: Tool Calling - Real World Impact

* What is a container? Why is a container useful for agent-engineering?
	* A container is an isolated runtime enviroment that is used for both security and safety. It is a standardized, isolated software unit that packages an application along with its dependencies. Using a container makes it possible for a user to allow a model to make system command tool calls without worrying that the model will accidentally delete something important. It also makes it possible for the model to visit or access any website without the concern that the website could contain malicious code that could affect the system. A third benefit of a container is it allows for a hard constraint on the context of a model. For example, if a user is attempting to debug a codebase it would be unhelpful if the model goes off to a different codebase stored on the same computer and starts making changes there. By implementing a container the user is keeping the agentic model focused and limited. Containers also run identically on all systems so when developing in a container there won't be "works on my machine" bugs. Containers also allow for parallel execution which is beneficial when attempting to combine multiple agentic systems. A common container tool that has these benefits is Docker. It should be noted that although the containers are isolated, they still have access to the shared host kernel so they aren't fully secure for all untrusted code execution.
* What is 'human-in-the-loop'?
	* Human-in-the-loop is a agent design paradigm that involves the explicit leveraging of a human actor. Most commonly this occurs during the tool-call process where the model sets up the tool it wants to call and the parameters it wants to send and then gives that to the user. The user decides whether to run to the tool call or not. Another human-in-the-loop system would allow for a human to interupt and correct an agent's decisions mid-pipeline. One key advantage of human-in-the-loop is it makes the responsibility of the agent's actions clearly assignable to a human operator instead of a probabilistic model. The paradigm also leads to what is considered a more socially acceptable usage of agentic models. One key downside is that human-in-the-loop significantly increases the time it takes for an agent to accomplish a task. By requiring the agent to seek approval from a human operator makes it so a task that could be run in a matter of seconds could take minutes or hours depending on the responsiveness of the user. For this reason a balanced system is most commonly adopted where the human is only asked to take action of "significant" or possibly "unsafe" tool calls. These could include irreverible actions like deleting files or sending emails or actions that have financial or security implications.
* What are some of the benefits of using a 'write and execute python' tool?
	* In a general sense a write and execute python tool is capable of handling problems that have a deterministic answer or problems that can be more efficiently solved using code. One example is when attempting to sort a list of names alphabetically. The python script for such a function would be easy to write and would not take very much computational time to run on the provided list. In contrast, if the model attempted to sort the names using its semantic system it would be very computationally intensive and could not promise that it would be capable of getting the right final answer. A python tool wopuld also be able to keep track of multiple variables and state accross a session which would be very helpful in multi-step computational tasks and would be a factor that would overcome context creep. Another benefit of a write and execute python tool is its portability. Such a tool would be able to access python libraries and other resources so the user wouldn't have to build specific tools for each scenario and instead could rely on the python tool to accomplish those tasks. This also comes as a downside because the user is giving permission for a foreign entity to write and execute code on their machine. This is where the isolated element of containers comes in as a benefit for the user. Also, by generating code, the user would be able to verify the code and its accuracy rather than a response generated by a semantic response which is nondeterministic.

### Section 2f: MCP and Alternatives (Code-as-tool)

* What problem does MCP solve in agent-based systems?
	* Model Context Protocol or MCP was designed to solve the integration problem that occurs between unique agents and unique tools. Without a standardized system like MCP, every integration setup would require custom connectors. This means that to connect 10 different agents to 10 different tools there would need to be 100 connectors built. This is different from an MCP system where the same setup would only require 20 connections. With the introduction of MCP, any MCP-compatible agent can connect to any MCP-compatible server without needing to have a custom integration to be built first. MCP works by connecting the client to a server that then acts as a gateway to external resources. It is similar to making an API call to a server that then queries a database and gives a response back. An added benefit of the MCP standardization is that it allows for flexible, adaptive workflows because as a server gains more functionality, it adds that to its MCP capabilities so the model making the MCP call can use a new service when it becomes available. Another added benefit of MCP is that it makes it easier to offload computation because the external MCP server is making resource calls so it does not have to be handled on the user's system. MCP also makes security standardization easier by forcing structured communication which reduces the vulnerabilities that come from ad-hoc integrations. 
* Give two reasons to implement an MCP server rather than use tool calling.
	* Reason One: When the MCP server has access to private information that you do not have access to. For example when making a tool that utilizes Google Map's MCP server you are able to access location data and traffic information that you do not have on your own system. It would be possible to build your own API tool to access this information, but an MCP system makes it so the respons is standardized and can be reused. This means that once it is built any agent can connect to it without needing their own API implementation. Reason Two: When the external tool is performing a task that requires a large amount of computational power. For example when working with a large machine learning system it makes more sense to set up an MCP server on the high powered ML computer so your model can make requests to that server rather than your own machine. Two other reasons to implement a MCP server insetad of tool are for cross-platform reusiblity and the added benefit of working with shared context and memory. 
* Name two downsides to implementing an MCP server.
	* MCP servers have a few downsides in setting up their implementations. Downside One: MCP servers require a lot of overhead to set up correctly. An MCP server has to be configured to communicate correctly with an MCP client. To do this several elements might need to be added to the server which wouldn't be necessary if building it as a simple tool instead. These overheads also include the process of keeping it up to date across different MCP clients and making sure that it is functioning properly. This would include the difficulty of debugging errors because it won't be as clear when there are a few small errors which often fail silently or cascade in a MCP server as opposed to a tool where it would be easier to see the errors. Downside Two: MCP servers have to be hosted while tools can be used locally. Because the server is set up as a server it needs to have access to a network where it will connect to the MCP client. If this is interrupted the MCP server will not function properly while tools are instead hosted locally where the model always has access to them. The other challenge associated with hosting the MCP server externally is that there will be additional latency in the model connecting to the server and the server sending its response. An additional downside I didn't mention is the increased surface of an MCP server. A tool is local, but an MCP server could be attacked using any of its exposed endpoints.

### Extra Questions

* What is agentic reasoning?
	* Agentic reasoning is the process by which an AI model handles autonomous decision-making, planning and action. One way it does this is by creating a chain-of-thought progression that happens in an internal process. This makes semantic probability based systems like LLMs perform better on logic problems because it gives them the ability to force intermediate steps before commiting to a final answer. The model also can accomplish reasoning by framing a prompt in a goal directed way so that the agent creates its own set of objectives and breaks those down into steps before it acts upon them. Reasoning also includes a think-act-observe loop where the model is able to make tool calls and then analyze the result before taking further action. Agentic reasoning also allows for the agentic system to self-correct because it is able to evaluate its own outputs and adjust its process.
